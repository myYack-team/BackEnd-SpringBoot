# 일일 활성 계정 통계

## 집계 기준

한국 시간(Asia/Seoul) 기준 기존 서버 요청에서 관측한 고유 계정을 하루 한 번 집계한다. 성공한 로그인·토큰 갱신과, 사용자 Access Token으로 인증하고 2xx 응답으로 완료한 사용자 API 요청이 대상이다. 로그인·토큰 갱신은 본업무 트랜잭션의 커밋 후 기록한다. 같은 계정이 반복 요청하거나 여러 기기에서 접속해도 하루 한 계정이다. 방문 날짜는 기기 시계나 요청 본문 대신 서버가 결정한다.

관리자·헬스·로그·로그아웃·계정 삭제 요청과 HEAD·OPTIONS 요청은 제외한다. 인증 실패·권한 거부·4xx·5xx 응답도 기록하지 않는다. 아직 완료되지 않은 비동기 응답도 기록하지 않는다. 통계 기록에 실패해도 로그인이나 사용자 API의 정상 결과를 바꾸지 않는다.

앱 업데이트나 별도 방문 API 호출 없이 서버 배포 이후의 요청부터 기록한다. 기존 로그를 소급 처리하지 않으므로 도입 이전 날짜의 0은 과거 사용량이 없었다는 뜻이 아니다. 관리자 화면에서는 오늘·어제와 최근 7일을 표시한다.

이 값은 신규 가입자 수나 앱 실행 횟수가 아닌 **일일 활성 계정(서버 요청 기준)**이다. 오프라인 사용, 비로그인 화면, 서버 호출 없이 화면을 유지한 시간은 관측하지 못한다. 자정이 지나더라도 다음 대상 요청이 있어야 새 날짜에 기록된다. 서버는 요청이 포그라운드에서 발생했는지 구분하지 않으므로 백그라운드에서 완료한 대상 요청도 포함된다. 테스트 계정도 정상적으로 인증하고 대상 요청을 완료하면 포함된다.

## API

| 요청 | 권한 | 결과 |
|------|------|------|
| `GET /api/admin/visits` | 관리자 세션 | 오늘·어제 고유 활성 계정 및 최근 7일 일별 활성 계정 |

관리자 응답은 `today`, `timeZone`, `todayVisitors`, `yesterdayVisitors`, `daily[{date,visitors}]`로 구성한다. API의 필드명은 유지하되 값은 위 집계 기준을 따른다. `daily`는 오래된 날짜부터 오늘까지 7개이며 빈 날짜는 0으로 채운다. 관리자 응답에는 사용자 식별 정보가 없으며 캐시를 금지한다.

## 저장과 중복 방지

`user_visits`는 사용자·기록일과 생성/수정 시각만 저장한다. 통계를 위해 IP·기기 ID·화면 이동·의료 데이터를 추가 수집하지 않는다. 사용자 행 잠금을 먼저 얻은 뒤 당일 기록 여부를 확인하고 생성하며, DB의 `(user_id, visit_date)` 유일 제약을 함께 둔다.

기록에 성공한 계정은 서버 내 일일 캐시에 보관해 같은 날의 반복 쓰기를 줄인다. 캐시는 최대 20,000계정이며 중복 방지의 최종 기준은 DB다. 서버 재시작이나 캐시 미적중으로 다시 시도해도 하루 한 계정이라는 기준을 유지한다.

전용 작업 스레드 1개와 대기열 256개로 통계를 저장하므로 반영에 짧은 지연이 있을 수 있다. 같은 계정·날짜의 대기 작업은 합치며, 자정 뒤 실행해도 서버에서 요청이 완료된 날짜를 유지한다. 기록 트랜잭션은 로그인·업무 트랜잭션과 분리한다. DB 실패 시 기록을 30초 쉬고 이후 대상 요청에서 재시도한다. 대기열 포화로 거부된 작업은 다음 대상 요청에서 다시 시도하되 이미 수락한 작업은 계속 처리한다. 대기열은 메모리에 있으므로 재시작·실패로 유실된 기록을 자동 복원하지 않으며 일부 활동이 누락될 수 있다. 이미 탈퇴한 계정의 대기 작업은 무시한다.

계정 삭제도 동일한 사용자 잠금을 얻고 방문 기록을 함께 삭제한다. 따라서 탈퇴한 계정의 방문은 조회 시점의 과거 통계에서도 제외된다. 새로운 이력 테이블은 기존 약물·인증 데이터와 별개다.

## 배포 준비

1. 서버 배포 전에 새 테이블 생성 권한과 스키마 적용 방식을 확인한다. `ddl-auto=update`를 사용하는 환경에서는 엔티티 변경으로 생성되지만 다른 환경은 아래 DDL을 별도로 적용해야 한다.
2. 서버 API를 먼저 배포하고 관리자 접근·집계 응답을 확인한다.
3. 기존 앱의 정상 로그인·토큰 갱신·사용자 API 요청이 오늘 집계에 반영되는지 확인한다. 앱 배포는 필요하지 않다.
4. 같은 계정의 반복 요청으로 수가 늘지 않는지, 관리자·헬스·실패 요청이 제외되는지 확인한다.

```sql
CREATE TABLE IF NOT EXISTS user_visits (
    id BIGINT NOT NULL AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    visit_date DATE NOT NULL,
    created_at DATETIME(6),
    updated_at DATETIME(6),
    PRIMARY KEY (id),
    CONSTRAINT uk_user_visits_user_date UNIQUE (user_id, visit_date),
    INDEX idx_user_visits_date (visit_date),
    CONSTRAINT fk_user_visits_user FOREIGN KEY (user_id) REFERENCES users (id)
);
```

운영 DB에 이 DDL을 자동 실행하는 스크립트나 운영 접속값은 제공하지 않는다.

## 검증

서비스 테스트는 한국 자정 경계·중복·누락 계정·7일 빈 날짜 처리를 검사한다. API와 수집 테스트는 관리자 집계 권한, 성공한 인증 요청과 제외 요청, 본업무 커밋 이후 기록 및 통계 실패 시 정상 응답 유지를 검사한다.

`UserVisitIntegrationTest`는 동시 방문 6개 요청, 다른 계정, 자정 날짜 분리와 실제 계정 삭제를 검사한다. 로컬에서는 격리된 H2를, 기존 CI에서는 `MYSQL_INTEGRATION_TEST=true`와 임시 MySQL을 사용한다. 외부 DB 연결값은 loopback 테스트 DB만 허용한다.
